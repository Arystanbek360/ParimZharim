БАГ №1 — ДУБЛИРОВАНИЕ ТАРИФА НА 1 МАЯ (и любую дату с двумя планами)
================================================================================

СИМПТОМ:
  На 1 мая 2026 в мобильном приложении/API показываются цены из ДВУХ тарифов
  вместо одного. Для всех остальных дней тариф отображается корректно.

ФАЙЛ:
  modules/ParimZharim/Orders/src/Application/Actions/GetPlanDetailsForObjectOnDate.php
  Строка: 14-16

ПРОБЛЕМНЫЙ КОД:
  $plans = $object->plans()
      ->wherePivot('date_from', '<=', $date)
      ->get();  // ← возвращает ВСЕ планы, а не только последний

ПОЧЕМУ ЛОМАЕТСЯ:
  Запрос возвращает все планы, у которых date_from <= запрошенная дата.
  На 1 мая 2026:
    - Старый план (date_from = 2024-05-02): 2024-05-02 <= 2026-05-01 → TRUE
    - Новый план (date_from = 2026-05-01): 2026-05-01 <= 2026-05-01 → TRUE
  Оба попадают в коллекцию. Далее:
    $prices = $plans->map(fn($p) => $p->metadata['mobile_app_price'])
  Возвращает mobile_app_price из ОБОИХ планов — двойной прайс.

  До 1 мая (например, 30 апреля):
    - Новый план: 2026-05-01 <= 2026-04-30 → FALSE → не попадает → только старый → OK

ПРАВИЛЬНАЯ ЛОГИКА:
  Должен возвращаться только ОДИН (последний) план — тот, у которого date_from
  максимальный среди подходящих. Аналог правильного кода есть в:
  OrderableServiceObjectPriceCalculationService::getCurrentPlanOrFail():
    ->wherePivot('date_from', '<=', $dateFrom)
    ->orderBy('date_from', 'desc')
    ->first();  // ← берёт только последний

  Также баг присутствует в том же файле для kitchen_deposit и guest_limits
  (там .first() спасает, но порядок не гарантирован).

БАГ №2 — БРОНИРОВАНИЕ С ОКОНЧАНИЕМ В 02:00 ПАДАЕТ С ОШИБКОЙ
================================================================================

СИМПТОМ:
  Пользователь выбирает слот 23:00, макс. длительность 3 часа → конец в 02:00.
  При попытке создать заказ система возвращает ошибку "нерабочее время"
  или "недостаточно свободного времени".

ФАЙЛ:
  modules/ParimZharim/Orders/src/Domain/Services/OrderableObjectSlotsCalculatorService.php
  Строка: ~246-249

ПРОБЛЕМНЫЙ КОД (в методе checkIfOrderCanBePlacedOnTimeOrFail):
  $slots = self::getSlotsForObjectOnDate($serviceObjectID, $startDate, $extendedEndDate, 30);

  foreach ($slots as $slotIndex => $slot) {
      $slotStart = Carbon::parse($slot['start'])->shiftTimezone(...);
      $slotEnd   = Carbon::parse($slot['end'])->shiftTimezone(...);

      if ($slotStart->greaterThan($endDate)) {  // ← строгое >, а не >=
          break;
      }

      if (!$slot['is_free']) {
          throw new InvalidOrderParams(...);  // ← падает здесь
      }
  }

ПОШАГОВОЕ ОБЪЯСНЕНИЕ:
  1. getSlotsForObjectOnDate вызывается с $startDate=23:00, $endDate=02:00, step=30.
  2. calculateTimeSlots генерирует слоты в цикле:
       for ($current = 23:00; $current <= 02:00; $current += 30min)
     Генерируются: 23:00, 23:30, 00:00, 00:30, 01:00, 01:30, 02:00 ← включается!
  3. Слот 02:00 проверяется по расписанию Schedule 25.
     Правило для пятницы: time_from="00:00", time_to="01:59"
     Проверка: "02:00:00" <= "01:59" → FALSE (строковое сравнение)
     → слот 02:00 = is_free=false, reason="нерабочее время"
  4. В цикле checkIfOrderCanBePlacedOnTimeOrFail:
     $slotStart = 02:00, $endDate = 02:00
     $slotStart->greaterThan($endDate) → 02:00 > 02:00 → FALSE → не выходим!
     → идём дальше → !$slot['is_free'] = true → throw InvalidOrderParams

ПОЧЕМУ РАНЬШЕ НЕ ЗАМЕЧАЛИ:
  Со старым расписанием (time_to="05:59"), тот же баг существовал для 06:00,
  но пользователи крайне редко бронировали ровно до 06:00.
  С новым закрытием в 02:00 и минимум 3 часа — сценарий 23:00→02:00
  является ОБЫЧНЫМ и критическим.

ГДЕ ИСПРАВИТЬ:
  Строка ~248: заменить
    if ($slotStart->greaterThan($endDate)) {
  на
    if ($slotStart->greaterThanOrEqualTo($endDate)) {
  Тогда при достижении слота 02:00 (= endDate) цикл завершится до проверки is_free.

ПРОБЛЕМНЫЙ КОД:

      ->wherePivot('date_from', '<=', $date)
      ->get(); // ← все расписания, включая устаревшие

  $minDuration = $schedules->map(function ($schedule) use ($dayOfWeek) {
      $weekDaysData = collect($schedule->metadata['rules']['week_days']);
      $relevantData = $weekDaysData->first(fn($wd) => in_array($dayOfWeek, $wd['weekdays']));

  На 1 мая подходят оба расписания. Если у старого min_duration=120,

  Аналогичная проблема с confirmation_waiting_duration.

В расписании Schedule 1 (старое, Баня №1-2) есть:

================================================================================
МЕТОДОЛОГИЯ — как работает выбор расписания/тарифа
================================================================================

loadSchedulesForDate (EloquentOrderableServiceObjectRepository):
  1. Загружает расписания, где date_from входит в [startDate, endDate]
  2. Загружает крайнее расписание с date_from <= startDate (для покрытия начала периода)
  3. Объединяет и сортирует по date_from DESC

getScheduleForDate (OrderableObjectSlotsCalculatorService):
  return $schedules->first(fn($s) => $date >= $s->pivot->date_from);
  Берёт ПЕРВОЕ подходящее из отсортированного DESC списка = самое свежее. ✓

getSlotRule:
  1. Сначала проверяет concrete_days (точные даты формата "DD-MM-YYYY")
  2. Если не нашёл — проверяет week_days (дни недели)
  Сравнение времени строковое: $time >= time_from && $time <= time_to
  Работает для диапазонов в пределах одного дня (не пересекающих полночь).

Ночные слоты (00:00-02:00) моделируются как ОТДЕЛЬНЫЕ правила для следующего дня:
  - Четверг 23:00→09:00-23:59, а продолжение до 02:00 записано как Пятница 00:00-01:59
